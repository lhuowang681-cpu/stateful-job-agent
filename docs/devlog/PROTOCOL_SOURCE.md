# Job Agent V2 — Codex 开发与学习留痕协议

> 目标：Codex 自主高效开发，开发过程可审计、可复现，用户事后可根据源代码路径和真实结果学习。不要为等待人工解释而暂停实现。

## 0. 行动优先级

1. 正确实现阶段目标（真实端到端业务闭环优先），不为堆技术栈而开发。
2. 改动有测试与可复现的验证证据；不得宣称未运行过的测试成功。
3. 为关键技术决策、关键代码和结果留下可学习的持久记录。
4. 记录简明，不要频繁中断开发，不输出内部隐含推理过程，仅总结可验证的设计理由与权衡。

## 1. 每个阶段开始前：写最小计划

维护 `docs/devlog/INDEX.md`，新增当前阶段的目标、范围、验收条件、基线状态和计划报告文件链接。
基线至少注明已有功能/问题、要使用的测试命令。无法确认的事项标记为“未核实”。

## 2. 每完成一个可独立运行的功能：随代码同步留痕

在当前阶段报告 `docs/devlog/PHASE-XX-<slug>.md` 中更新“功能轨迹”（建议一项 5～12 行），必须包含：
- 问题/用户场景（要解决什么）；
- 方案和关键权衡（为什么这样做，至少一个备选方案及不选原因）；
- **代码锚点**：`相对路径::类名/函数名`，输入/输出或关键数据结构；
- **调用链**：从前端/API 入口到服务、Agent/工具、数据库和输出文件的实际路径；
- **验证**：运行命令、结果、测试或演示数据/日志路径；
- **限制或失败案例**（没有验证的部分必须说明）。

路径必须是仓库里真实存在的路径，类和函数名必须核实。相较行号，优先可长期检索的 `path::symbol`。不要罗列所有改动文件，只列最值得学习的 3～10 个入口与核心实现。

建议按可工作的功能增量落盘，不要拖到整个阶段结束才写，以防上下文中断导致记录丢失。

## 3. 每个阶段结束：交付阶段复盘包

使用 `docs/devlog/_PHASE_TEMPLATE.md` 模板生成或更新该阶段报告，并同步更新：
- `docs/devlog/INDEX.md`：阶段状态、验收结果、报告链接和按顺序学习的代码路径；
- `docs/devlog/ARCHITECTURE_MAP.md`：当前真实架构与关键调用链，标注已接通/尚未接通；
- `docs/devlog/DECISIONS.md`：仅记录重要的新增架构决策、备选方案及适用条件。

阶段报告至少包含：
A. 业务问题 + 基线证据；B. 方案及为何优于替代方案；C. 核心代码地图（入口→调用链→数据流）；
D. 实际功能、失败和遗留问题；E. 可一键复现的命令、测试和环境依赖；F. 前后对比（同数据、同条件；无有效对照就标记尚无结论）；
G. 5 个项目面试追问及参考回答要点；H. 用户事后学习顺序（建议 30～60 分钟）。

最终汇报格式：`完成情况 / 重点改动 / 可复现验证 / 尚未完成 / 先读哪些文件 / 需要用户决策的事项`。

## 4. 可复现性与真实性

- 不能把 mock、单元测试或局部验证说成真实模型 + 真实后端的端到端测试。
- 记录模型版本、实验配置、样本规模、基线与新方案的同口径指标；未提升也如实写出。
- 为 Demo 保留可运行步骤（服务启动、依赖、账号/脱敏示例、操作步骤及预期结果）；不写虚构演示。
- 现有功能应优先复用；移除旧路径时记录为何移除和替代路径。
- 不把个人简历、身份证明、联系方式、令牌、数据库密码或完整敏感日志写入开发日志；使用脱敏样例。
- 不因记录要求降低安全性、破坏测试或修改用户事实依据。

## 5. Git 追溯

- 阶段开始记录当前分支、`git rev-parse --short HEAD`（若可用）、`git status --short`；阶段结束记录 `git diff --stat` 和关键文件变更。
- 仅在已有授权时创建本地提交，不自行 push、reset、rebase 或覆盖用户修改；未提交时使用 diff 与现有 HEAD 标记。
- 每个阶段要能从阶段报告追踪到具体代码和测试，而不是只有一份最终 README。
